## 核心结论速览

1. **小兵在空旷直道上「瞬时速度」是严格匀速的，没有加速度爬坡**：War3 底层 `NIpse::CPoPosCl` 虽有 `acc` 字段，但引擎在每次下达移速时都将 `acc := maxSpeed`，1 个 tick 即达满速（无 buff 时精确 `325 / 32 = 10.15625` 单位/tick，32 Hz 模拟步长）。
2. **所有 6 种普通兵、6 种超级兵（含攻城车 `ebal` / `umtw`）基础移速全部是 `325`**，且地图脚本全部采用**逐只 `IssuePointOrderLoc`**（非 `GroupPointOrder`），**不存在攻城车或编队拖慢整波的现象**。
3. **造成实测「非匀速」的四大真实原因**：
   - **① 前 7 分钟边路移速光环（最大变量，脚本层）**：`TimerGetElapsed(M) < 420s` 时，DotA 6.83d 在 `SPO` 中给**优势路（近卫下路、天灾上路）**刷出的近战/远程兵附加 `A2V1`（`+25%` → **`406.25`**，持续 **15s**，约覆盖前 `5800~6000` 距离）；给**劣势路（近卫上路、天灾下路）**附加 `A2V0`（`-25%` → **`243.75`**，持续 **15s**，约覆盖前 `3600` 距离）。中路与攻城车不加此光环。
   - **② 出生原地停下转身（引擎 `propWin` 二值门控）**：所有小兵由 `CreateNUnitsAtLoc(..., bj_UNIT_FACING)` 刷出，初始朝向固定 **`270°`（正南）**。引擎 `CPoPosCl::StepTurnAndMove` 对推进窗口（`propWin = 60°`，攻城车 `30°`）实行**硬二值门控**：只要 `|Δθ| >= propWin`，速度强制置 `0` 原地转身，直到转入 `±propWin` 才瞬间全速起步。近卫上路（转 179°）、近卫中路（转 138°）、近卫下路/天灾上路（转 ~90°）出兵第 1 秒因此显著偏慢；天灾中路（44.5°）和天灾下路（2.3°）则几乎零停顿。
   - **③ 队友碰撞停等 + 侧向绕行（引擎 `forceStop = 1` + `CPoSeparate`）**：同波近战刷在同一个矩形中心点，互相挤压触发寻路碰撞返回非 0，引擎传入 `forceStop = 1` 使后排兵整 tick 停顿（`speed = 0`）等待前排让位，并侧向绕出（近卫下路 `3300~4300` 弯道处外侧兵被挤到横向 `-150 ~ -175`）。高频采样平均后，表现为出兵第 1 秒 230~280/s、弯道段 230~285/s。
   - **④ 测量偏差（VM 墙钟漂移）**：`AiUnit.log` 用墙钟（`GetTickCount`）计 `t`，在 VirtualBox 帧率/时钟降速波次（如 W01/W02/W05，相邻两波实测间隔 37~45s 而非 30s）中，用墙钟算出的「1525 用时 6.2s（理论 4.7s）」里，很大一部分是 **0.7~0.8× 墙钟慢放造成的表观延迟**，而非游戏逻辑变慢。

## 二、地图脚本分析（`War3Script/war3map.j`）

### 2.1 出兵与下令链路（不是 `GroupPointOrder`）

1. **刷兵（`SPO`，L23194）**：每 30s 执行一次（`ZG` 周期触发器），第 7n 波额外刷攻城车。
   - 刷兵全部调用 `CreateNUnitsAtLoc(count, typeId, player, spawnLoc, bj_UNIT_FACING)`，其中 **`bj_UNIT_FACING = 270.0°`（正南）**。
   - 紧接着调用 `SZO(bj_lastCreatedGroup)`（优势路加 `A2V1` +25%/15s）或 `SVO(bj_lastCreatedGroup)`（劣势路加 `A2V0` -25%/15s），再调用 `SSO(bj_lastCreatedGroup, laneLevel)` 写入分路标记技能 `I2 = 'A007'`（等级 `2`=上路、`3`=中路、`4`=下路）。
   - **关键**：`SPO` 本身**不直接下移动指令**！指令是由「单位进入出生矩形」触发器下达的。
2. **出生即触发下令（L96180–96256）**：
   - 单位在出生矩形内创建瞬间，立刻触发 `TriggerRegisterEnterRegion` 绑定的 `S3O / S6O / S8O / SAO / SCO / SEO`（L22976–23010）。
   - 回调体全部是**单只单位指令**：
     ```jass
     call IssuePointOrderLoc(GetTriggerUnit(), "attack", BI / CI / DI)
     ```
   - 全脚本检索 `GroupPointOrder` 为 **0 命中**，兵线小兵**从未以编队群组下令**。
3. **中途重复下令区域（中继矩形）**：
   - 每条路除了近战/远程两个出生矩形外，还在兵营前方额外注册了 1 个中继矩形（`SA / KA / TA / LA / NA / MA`），绑定在**同一个**触发器上。
   - 小兵走出兵营约 550~930 距离进入该中继矩形时，会**再次**收到 `IssuePointOrderLoc(u, "attack", 同一路点)`。
   - **是否导致停顿/转身**：由于目标点 `BI/CI/DI` 与当前攻击移动目标**完全相同**，且小兵已朝向路点，引擎不会清零速度或原地重转；仅在极少数刚绕完兵营的瞬间触发一次路径微调（无明显停顿）。
4. **拐点换路点（`NUO`，L22962 & L96170–96174）**：
   - 三个拐点占位单位 `BZ`（上路角）、`ZZ`（中路河道）、`DZ`（下路角）注册了 `TriggerRegisterUnitInRange(t, unit, 300, ...)`。
   - 当小兵进入拐点 **300 半径**内，触发 `NUO`：
     - 近卫兵（`BO[0]`）→ `IssuePointOrderLoc(u, "attack", U0)`（天灾基地 `OZ`）
     - 天灾兵（`CO[0]`）→ `IssuePointOrderLoc(u, "attack", II)`（近卫基地 `CZ`）
   - **换路点时的停顿/转身**：
     - **中路（`ZZ`）**：几乎直线（偏转 < 10° < `propWin`），**不减速、不停顿**。
     - **上路角（`BZ`）与下路角（`DZ`）**：约 **90° 直角拐弯**（`90° > propWin 60°`），进入 `300` 半径换令瞬间，小兵必然触发引擎 `StepTurnAndMove` 原地停顿转身（约 0.1~0.25s，攻城车 `propWin=30°` 停更久），但该拐点位于己方一塔之后（距兵营 9100~9950），**不在常规卡兵段（兵营 → 己方一塔）内**。
5. **仇恨/脱战重下令**：`CA2 / CD2 / OO2 / CP2 / D02` 均按 `O2[GetUnitAbilityLevel(u, I2)]` 单独对每只小兵重新下发 `IssuePointOrderLoc(u, "attack", ...)`，其中 `CP2 / D02`（拉仇恨反防异常）会调 `SetUnitPosition(u, x, y)` 清掉旧指令再重下。

## 三、War3 引擎逆向分析（`game.dll` 全版本）

Warcraft III 的单位移动、转身、编队限速与碰撞分离由内嵌的 **NIpse 物理/寻路子系统** 实现，核心对象链为：
`CUnit+0x164`（内嵌位置句柄）→ 代理表查找 → `NIpse::CPoPosCl*`（派生自 `NIpse::CPoPos`）。

从 1.26 `0x494AD0` 调试输出函数捕获到 Blizzard 原始字段名字符串（`0x953294: "[PosCl]"`、`0x95325C: "\tglr[%s] prw[%s] acc[%s] ang[%s]"`），直接确认对象内存布局：

| `CPoPosCl` 偏移 | Blizzard 内部名 | 含义 | 默认值（1.26 常量） |
| :---: | :--- | :--- | :--- |
| `+0x78 / +0x7C` | `pos.x / pos.y` | 寻路格坐标（世界坐标 = `pos × 32 - 8192`） | — |
| `+0x80 / +0x84` | `vel.x / vel.y` | 速度矢量（寻路格/秒；`× 32` 为世界单位/秒） | 0 |
| `+0x88` | `maxSpeed` | 当前最大速度上限（格/秒） | — |
| `+0x8C` | `targetFacing` | 目标朝向（弧度） | — |
| `+0x90` | `facing` | 当前朝向（弧度） | — |
| `+0xB0` | `glr` | 到达目标半径（格） | `0.8f` (`0x3F4CCCCD`，`6FAAE4EC`) |
| `+0xB4` | `acc` | 步进加速度（格/步） | 默认 `0.75f` (`6FAAE4E8`)，**运行期被设为 `= maxSpeed`** |
| `+0xB8` | `ang` | 转身角速度（`turnRate`，弧度/转身步） | 最小下限 `0.001f` (`0x3A83126F`，`6FAAE47C`) |
| `+0xBC` | `prw` | 推进窗口（`propWin × π/180`，弧度） | 默认 `1.2f` rad (`0x3F99999A`，`6FAAE4FC`) |

### 3.1 四大引擎机制反汇编结论

#### (1) 单位移动有没有加速度？→ **无渐进加速，1 tick 瞬间满速**（置信度：**高**，1.26 / 1.27 逐指令确认）
- 在 `CPoPosCl::StepTurnAndMove`（1.26 `0x493FA0` / 1.27 `0x11CFD0`）中，当满足推进条件时，引擎确实执行 `*speed += this->acc`（`+0xB4`）。
- **但**在 `CUnit` 下发移动速度的两处入口（1.26 `0x474ECA..0x474F18`、`0x475133..0x475173`；1.27 `0x03E8E8..0x03E926`），引擎把 `v = min(unitSpeed, groupSpeed) / 32.0f`（通过给 IEEE-754 指数位加 `0xFD800000` 即 `-5 << 23` 实现 `/ 32`）**同时写入 `SetMaxSpeed(+0x88)` 和 `SetAcc(+0xB4)`**：
  ```c
  float v_cells = min(unitSpeed, groupSpeed) / 32.0f; // 325 / 32 = 10.15625
  CPoPos::SetMaxSpeed(pos, &v_cells);  // [pos+0x88] = v_cells
  CPoPosCl::SetAcc(pos, &v_cells);     // [pos+0xB4] = v_cells
  ```
- 而在 `CPoPos::AddVelocity`（1.26 `0x4A70D0` / 1.27 `0x10CE30`）中，速度矢量直接叠加并立刻截断到 `[pos+0x88]`，若 `|v|² < eps`（1.26 `6FAAE614` / 1.27 `6FB59468`）则瞬间归零，无任何阻尼或惯性项。
- **结论**：只要允许移动，第 1 个步进周期即从 `0 + acc = maxSpeed` 一步到位满速；实测日志中 `AiUnit.log` 每次坐标跳变精确为 `10.15625` 的整数倍（1~5 ticks = `10 / 20 / 30 / 41 / 51` 单位），与引擎完全吻合。

#### (2) 转身时是否减速 / 停下？→ **硬二值门控（超出 `propWin` 速度归零，窗口内 100% 满速）**（置信度：**高**，1.21 / 1.26 / 1.27 逐指令确认）
- `CPoPosCl::StepTurnAndMove`（1.26 `0x493FA0` / 1.27 `0x11CFD0`）完整反编译逻辑：
  ```c
  void CPoPosCl::StepTurnAndMove(float *outSpeed, float *outAngle, const float *pAngleDiff, int forceStop) {
      float absDiff = fabsf(*pAngleDiff);
      // 1. 推进窗口二值门控（非比例减速！）
      if (forceStop == 0 && absDiff < this->prw /* +0xBC */) {
          *outSpeed = *outSpeed + this->acc;    // +0xB4，因 acc == maxSpeed，直接满速
      } else {
          *outSpeed = 0.0f;                     // 超出推进窗口或被阻挡 -> 完全停在原地！
      }
      // 2. 转身步进（无论是否停下，均按 turnRate 逼近目标角）
      if (absDiff != 0.0f) {
          float step = min(absDiff, this->ang /* +0xB8 */);
          if (*pAngleDiff < 0.0f) step = -step;
          *outAngle = *outAngle + step;
      }
  }
  ```
- **含义**：
  - 轻微拐弯（`|Δθ| < 60°`，攻城车 `< 30°`）：**边走边转，速度 100% 不掉**。
  - 大角度转身（`|Δθ| >= 60°`，如出兵 `270°` 转东/北/东北，或卡兵逼停绕背）：**完全停在原地（`speed = 0`）**，直到转入 `±60°` 锥角才瞬间满速冲出。

#### (3) 编队 / 群组移动是否统一到最慢单位？→ **引擎有此机制，但 DotA 兵线不触发**（置信度：**高**）
- 引擎机制：`MovementGroup`（1.26 虚表 `0x933C54` / 1.27 `0xA5CEA8`）在群组下令时，把组内最慢单位速度作为 `groupSpeed` 传给上述 `min(unitSpeed, groupSpeed)` 截断逻辑（1.26 `0x474ECA` / 1.27 `0x03E8E8`），使快单位降速与慢单位同步。
- **对 DotA 兵线的影响 = 0**：
  1. 地图脚本全部使用单只 `IssuePointOrderLoc`，每只兵独立成组，无跨单位 `groupSpeed` 共享；
  2. 所有 6 种兵（含攻城车）基础移速都是 `325`，即使前 7 分钟优势路小兵为 `406.25`、第 7 波攻城车为 `325`，因为指令独立，攻城车也不会拖慢整波（只是攻城车自己落在后面）。

#### (4) 互相碰撞 / 绕开队友时的减速规则？→ **离散停等（`forceStop = 1` 置 0）+ `CPoSeparate` 侧向绕行**（置信度：**中高**，主循环与调用链已确认，内部局部寻路细枝未全展开）
- 在 `StepTurnAndMove` 的主调函数（1.26 `0x495380..0x495510`）中，每次步进先调用局部避障/碰撞检测（1.26 `0x49E020`）：
  - 返回 `0`（前方畅通）：`forceStop = 0`，全速前进；
  - 返回非 `0`（前方被友军或障碍占据，如 `3` / `4`）：置 **`forceStop = 1`** 传入 `StepTurnAndMove`，**令该单位本步速度直接归 `0`**，同时仍允许转向绕行方向，并在需要时调用 `0x493E80` 触发局部重寻路与 `NIpse::CPoSeparate`（1.26 虚表 `0x9521B4` / 1.27 `0x960EB0`）侧向分离。
- **宏观效果**：友军卡位不是「平滑降到 70% 速度」，而是**「0.1~0.3s 原地停等（speed=0）→ 侧移绕出 → 恢复 325 满速」**的停走脉冲；投影到车道轴时叠加 `cos θ < 1`，在 100 单位区间统计上表现为均值跌至 `230~295/s`。

## 五、给卡兵 AI 的直接结论与改进建议

### 5.1 能不能用「按车道位置查表的速度」替代固定 `325`？

**结论：不能只用一张静态的「车道位置 → 速度」表替代 `325`，但应当用「三因子速度模型」替代固定 `325`：**

1. **为什么单一静态查表会翻车**：
   - **前 7 分钟 vs 7 分钟后差 ±25%（81 移速差）**：近卫下路/天灾上路前 7 分钟是 `406.25`（前 15s），7 分钟后是 `325`；近卫上路/天灾下路前 7 分钟是 `243.75`（前 15s），7 分钟后是 `325`。用同一张静态表必然在 7:00 前后必有一边严重误判。
   - **速度基准应读取实机移速或按时钟分档**：最优是直接从 `CUnit+0x1EC → CAbilityMove` 读当前真实移速（或按 `gameTime < 420 && waveElapsed < 15s` 查表 `406.25 / 243.75 / 325`），**不要用固定 325**。
   - **不要用墙钟 `dt` 盲推**：在 VM 掉帧/卡顿时，墙钟速度会偏低 20~30%；优先用游戏时钟或短窗平滑，且理论基线延迟应以**实际读到的 `v_base`**（而非固定 325）计算。

### 5.2 出兵处与拐弯处该怎么预测（0.25s 前瞻）

| 场景 | 现象与根因 | 建议预测策略 |
| :--- | :--- | :--- |
| **出兵前 1.0~1.5s**（尤其近卫上/中/下、天灾上） | 出生朝向 `270°` 触发 `propWin` 停顿 + 刷兵点重叠触发 `forceStop=1`，领头兵速度从 0 瞬间跳变到 `v_base`，而波中心落后 20~30% | **不要拿前 2 帧的速度外推**（0→325 是阶跃而非平滑加速）；在未进入满速前，直接把领头兵的预测速度下限钳位到 `0.85 × v_base`，且边路坚持在兵营外排好队后（如现有 `-mark position`）再接手卡兵。 |
| **近卫下路 `3300~4300` 及 `5800~6100` / `7400~8000` 弯道** | 兵线实际沿树林外缘弧线走，外侧兵横向被挤到 `-150 ~ -175`；沿直线轴的投影速度因 `cos θ` 掉到 240~285，但**沿实际切线方向的速度仍是满速 325**（一旦英雄挡歪，外侧兵以 325 切线速度瞬间溜走） | ① 速度预测应沿**小兵实际瞬时速度向量 `(vx, vy)`**（或 `lane_paths` 切线方向）做 0.25s 外推，**不要按直线车道轴降速**；② 横向对准时，在 `3300~4300` 处给外侧（横向最负）前排兵提高权重，防止外侧兵从 `-175` 侧翼脱钩。 |
| **攻城车波（第 7n 波）** | 攻城车 `spd=325` 但 `propWin=30°`、前 7 分钟无 `A2V1/A2V0` | 不必担心攻城车拖慢整波；前 7 分钟优势路第 7/14 波攻城车会被普通兵甩开 ~1200 距离，卡兵只需盯住前排普通近战。 |
| **被英雄卡住后的重起步** | 引擎无加速度，小兵一旦被英雄挡住触发 `forceStop=1` 或转出 `propWin`，松口瞬间会**在 1 个 tick（31.25ms）内从 0 瞬间恢复满速 `325 / 406.25`** | 卡兵判断「小兵是否已停下」时**绝不能依赖历史速度衰减**——只要小兵朝向与绕行方向夹角 `< 60°`，下一帧就会瞬间以满速冲出，英雄补位必须按**满速 `v_base`** 留提前量。 |
