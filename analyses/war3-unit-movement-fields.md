## 一、卡兵可以直接用的结论

`aiFindAgentInRing` 拿到的指针就是 `CUnit*`。1.22 到 1.27 上下面这些偏移一致；1.0.17 到 1.21 的二进制里也有同样的 `+0x164` / `+0x19C` / `+0x1EC` 特征，但那几版的 JASS 外壳还是旧虚拟机，字段没有逐条跟完。

| 要读的量 | 从 `CUnit*` 出发 | 置信度 |
| :--- | :--- | :--- |
| 类型 | `+0x30` 四字码（`esen` / `edry` / `ebal` / `Hjai`） | 高。`GetUnitTypeId` 就是这一条 `mov` |
| 网络对象 ID | `+0x0C`、`+0x10` | 高。和现有发包用的 ID 对是同一对 |
| 世界坐标 | **不是**单位上的两个 float。`vtable+0xB8` 得到内嵌位置对象（`CUnit+0x164`），再用 `GetWidgetWorldPos` | 高（调用链）。原始分量在代理表节点 `+0x78/+0x7C` 一带，合成公式没有用走动对照确认 |
| 朝向（弧度） | 位置对象里的 ID 对查代理表，节点 `+0x90` | 高（指令）。没有和 `GetUnitFacing` 的返回值对过 |
| 当前移速 | `CUnit+0x1EC` → `CAbilityMove*`。未减速时读 `+0x70`（小兵 325，冰女 280）。`+0x78` 是乘数（样本里是 1），`+0x7C != 0` 时原生直接返回 0 | 高。数值对得上 DotA 物编移速；原生还会乘别的修正，不是单条 `mov` |
| 基础移速 | 非英雄：按 `+0x30` 查单位数据，记录 `+0x1D4`。英雄另走 `CUnit+0x1F0` | 高（反汇编）。实机没有单独把 `+0x1D4` 读出来 |
| 飞行高度 | `CUnit+0x208` | 高。地面单位实机是 0 |
| 当前指令 ID | `+0x19C/+0x1A0` 查到 `COrder*`，再读 `+0x24`。实机攻击是 `0xD000F` | 高 |
| 指令目标点 | `COrder+0x48` = X，`+0x50` = Y（地图坐标） | 高。构造函数把这两格清成 0，实机攻击指令里是地图级坐标 |
| 指令目标单位 | 这几组攻击样本里，`+0x2C/+0x30`、`+0x38/+0x3C`、`+0x58/+0x5C` 都是 `0xFFFFFFFF`，`+0x54` 是 0 | 未确认 |
| 碰撞半径 | 没有找到 16 / 32 / 48 这一档的字段 | 未确认 |
| 寻路折线 / 下一路径节点 | 没有定位到节点数组。小兵“下一步去哪”目前只能看当前指令的目标点 | 未确认 |

句柄换对象：权威入口是 `JassHandleToUnit`（只在游戏线程、`GamePlaying` 里调）。`aiFindAgentInRing` 记的是同一个 `CUnit*`，但 8192 环会被后面的注册冲掉，不能当唯一来源。

## 二、句柄到 `CUnit*`

`GetUnitX` 的第一件事就是 `JassHandleToUnit(handle)`。1.26 的实现是 `0x3BDCB0`，1.27 是 `0x1D1550`（`GetUnitX` 里的 `call` 与已有技能文档一致）。1.24.4 的 `GetUnitX`（`0x3C6050`）调用 `0x3BE7F0`，同样是该版的 `JassHandleToUnit`。

返回的指针通过下面这条检查才当活对象用：用 `CUnit+0x0C/+0x10` 查代理表，节点 `+0x0C` 必须是类标记 `0x2B61676C`（`'+agl'`），节点 `+0x20` 必须是 0。`ResolveAgent` 再从节点 `+0x54` 取出真正的 C++ 对象。所以：

- 环里存的 agent 是 `CUnit*`，不是代理表节点。
- `+0x0C/+0x10` 是网络 ID，不是类标记。类标记在代理表节点上。
- 环被冲掉之后，应在游戏线程调用 `JassHandleToUnit`，不要在读图阶段调（会走到 `game.dll+0x2bd982` 那类空指针）。

| 版本 | `JassHandleToUnit` | 代理表查找 | 查找用的全局（RVA） | `ResolveAgent` |
| :--- | :---: | :---: | :---: | :---: |
| 1.26.0.6401 | `0x3BDCB0` | `0x3FA30` | `0xAB7788` | `0x4786B0`（节点 `+0x54`） |
| 1.27.0.52240 | `0x1D1550` | `0x37350` | `0xBE40A8` | `0x44150`（`GetUnitCurrentOrder` 在取出对象后读 `+0x24`） |

1.27 实机：代理表指针在 `Game.dll+0xBE40A8`，当时值 `0x05D400D0`。查找规则和 1.26 相同：ID 高位为 0 用表 `+0x0C`，高位为 1 用表 `+0x2C`；槽第一个 dword 为 `0xFFFFFFFE` 才有效，节点在槽 `+4`，并且节点 `+0x18` 必须等于第二个 ID。

## 三、`CUnit` 与移动相关对象

1.26 的 `CUnit` 虚表 RVA `0x931934`（RTTI `.?AVCUnit@@`）。`vtable+0xB8` 是 `0x28B0E0`：`lea eax, [ecx+164h]; ret`。1.27 虚表 RVA `0xA4A704`，对应函数 `0x668DA0`，指令相同。11 个版本的 `.text` 里都有这 7 个字节。

```text
CUnit
  +0x0C / +0x10   网络对象 ID
  +0x30           单位四字码
  +0x33           四字码首字节；'A'..'Z' 判英雄（GetUnitDefaultMoveSpeed）
  +0x5C           状态位。0x40000000 = 幻象（默认移速不走英雄分支）
  +0x164          内嵌位置对象
      +0x08/+0x0C 代理 ID 对  → 绝对偏移 CUnit+0x16C / +0x170
  +0x19C / +0x1A0 当前 COrder 的 ID 对。两个都是 0xFFFFFFFF 表示没有指令
  +0x1E8          CAbilityAttack*。索敌距离在技能对象 +0x244（GetUnitAcquireRange）
  +0x1EC          CAbilityMove*（'Amov'）
  +0x1F0          CAbilityHero*。英雄默认移速从这里算
  +0x208          飞行高度 float。GetUnitFlyHeight 直接返回它
  +0x2CC          另一种按单位类型固定的 float（vtable+0xBC：fld [ecx+2CCh]）。不是碰撞，见第六节
```

`GetUnitX` / `GetUnitY`（1.26 `0x3C5510` / `0x3C5550`，1.27 `0x1E66B0` / `0x1E66F0`）在句柄换成 `CUnit*` 之后：

1. `call [vtable+0xB8]`，得到 `CUnit+0x164`。
2. `GetWidgetWorldPos(pos, xyz)`。1.26 是 `0x4743A0`，1.27 是 `0x03B720`（与树木那条链是同一个函数）。
3. X 取 `xyz[0]`，Y 取 `xyz[1]`，Z 被写成 0。

`GetWidgetWorldPos` 内部用位置对象 `+0x08/+0x0C` 查代理表，再把节点上的分量和地图原点相加。1.27 实机地图对象在 `Game.dll+0xBB82BC`（当时 `0x05D10088`），`+0x6C` 和 `+0x70` 都是 **-8192**。1.26 反汇编里对应的全局 RVA 是 `0xAB7368`，同样加 `+0x6C` 和 `+0x70`。

节点上实机读到的分量（站桩攻击，300 ms 内不变）：

| 单位 | 节点 `+0x70` | `+0x74` | `+0x78` | `+0x7C` | `+0x80` | `+0x84` | `+0x8C` | `+0x90` |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| esen `0x6AF0014` | 223.37 | 0 | 170.33 | 167.84 | 6.05 | 8.16 | 0.93 | 0.50 |
| esen `0x6AF0324` | 223.37 | 0 | 167.80 | 164.43 | 6.05 | 8.16 | 0.93 | 0.50 |
| edry `0x6AF0F64` | 223.37 | 0 | 61.50 | 234.92 | 0 | 10.16 | 1.57 | 0.25 |
| edry `0x6AF1274` | 223.37 | 0 | 162.45 | 157.18 | 6.05 | 8.16 | 0.93 | 0.25 |

`+0x70` 四个人一样，不是各自的坐标。每人不同的是 `+0x78/+0x7C`。朝向函数读的是 `+0x90`（弧度），再乘一个运行期常数换成角度：1.26 的乘数地址是 `0x6FAAE60C`，1.27 是 `0x6FB59460`。文件里的这两处是 0，常数在启动后才填。这次采样的单位在攻击，坐标 300 ms 没变，所以没有用位移证明哪一个分量是 X。要和 `GetUnitX/Y` 逐值对照，应在游戏线程调 `GetWidgetWorldPos`，不要自己把上面的乘法展开当公式用。

## 四、移速

`GetUnitMoveSpeed`：1.26 `0x3C5810` 调 `0x26DE20`；1.27 `0x1E62E0` 调 `0x667BE0`。两者都是：

```text
amov = [CUnit+0x1EC]
if (amov == NULL) return 0
else 把速度写到调用者给的 float 槽里
```

1.26 的内层 `0x201C60`（1.27 是 `0x5DF170`）：

```text
if ([amov+0x7C] != 0) return 0
else 用 [amov+0x70]、[amov+0x78] 和单位身上的修正做软浮点乘除
```

实机四个近卫单位 `[amov+0x7C]` 都是 0，`[amov+0x78]` 都是 1，`[amov+0x70]` 为：

| 类型 | 对象 | `Amov+0x70` | 物编基准（DotA） |
| :--- | :--- | ---: | :--- |
| esen | 两只 | 325 | 近战兵 325 |
| edry | 两只 | 325 | 远程兵 325 |
| ebal | 三只（上一轮扫描） | 325 | 攻城车 325 |
| Hjai | `0x11035BF4` | 280 | 冰女 280 |

另一处扫到的 `Hjai`（`0x482EE60`）位置 ID 是 0、飞行高度是垃圾值，丢掉。

`GetUnitDefaultMoveSpeed`（1.26 `0x3C5870`，1.27 `0x1E6040`）：用 `+0x30` 查单位数据表（1.26 查找 `0x29C500`，表对象 `0x6FAB445C`），把记录 `+0x1D4` 的 dword 当作 float 返回。英雄且不是幻象时，改走 `CUnit+0x1F0` 上的 `0x26EAF0` / `0x208170`（1.27 是 `0x667BC0` → `0x50B3C0`），再和数据表的值做一次运算。同一次速度计算还会读记录 `+0x1D8` 和 `+0x1DC`（1.26 `0x29C540`、`0x29C580`），这两个相邻字段的名字没有单独对上，不能写成“最小/最大移速”。

## 五、当前指令和目标点

`GetUnitCurrentOrder`（1.26 `0x3C7780`，1.27 `0x1E5F80`，1.24.4 `0x3C82C0` 结构相同）：

```text
pair = (CUnit+0x19C, CUnit+0x1A0)
if ((pair.a & pair.b) == 0xFFFFFFFF) return 0
order = ResolveAgent(&pair)
return [order+0x24]
```

1.26 `COrderPoint` 构造函数在 `0x286F72` 把虚表写成 `0x6F92FFA4`，并把 `+0x48`、`+0x50` 设成浮点 0 所在的全局。实机 1.27 四条攻击指令：

| 单位 | `COrder+0x24` | `+0x48`（X） | `+0x50`（Y） |
| :--- | :--- | ---: | ---: |
| esen `0x6AF0014` | `0xD000F` | -561.8 | -651.8 |
| esen `0x6AF0324` | `0xD000F` | -561.8 | -651.8 |
| edry `0x6AF0F64` | `0xD000F` | -6005.2 | 5458.5 |
| edry `0x6AF1274` | `0xD000F` | -561.8 | -651.8 |

`0xD000F` 就是现有 hook 用来攻击的指令 ID。`-6005, 5458` 是地图坐标，不是节点里那种一两百的分量。`+0x44`、`+0x4C`、`+0x78` 在这四条里都是模块内的同一个静态指针 `0x6E21FD80`，不是某个单位。

寻路折线没找到。RTTI 里有 `CMoveReq`、`CPathingFootprint`，没有把它们挂到“下一路径点数组”上。小兵脚本发的移动/攻击点就在 `COrder+0x48/+0x50`，卡兵预测下一落点先用这个。

## 六、碰撞：没确认

在 `CUnit` 前 `0x320` 字节和位置节点前 `0x120` 字节里，没有 16、32 或 48 这种碰撞半径。

`CUnit+0x2CC` 按类型固定，而且攻城车比近战兵更小，所以它不是碰撞体积：

| 类型 | `+0x2CC` |
| :--- | ---: |
| esen | 160.155 |
| edry | 141.935 |
| ebal | 103.648 |
| Hjai | 146.458 |

近卫兵对象上还能看到数值 60（大约在 `+0x228` 附近），近战和远程一样，也不是“英雄一块、小兵一块”的碰撞差。物编碰撞仍然只能当脚本侧的常数，不能从这次定位的字段里读。

## 七、全版本 RVA

原生地址来自注册点 `mov edx, 名字; mov ecx, 函数`。每个名字还有一处共用桩（1.26 是 `0x71D9D0`，1.27 是 `0x70A0C0`），下表取的是各名字自己的函数。1.27 的 `.text` 文件偏移比 RVA 小 `0xC00`，反汇编必须按 RVA 换算，不能把 RVA 当文件偏移。

| :--- | :---: | :---: | :---: | :---: | :---: | :---: | :---: | :---: |

| 1.27.0.52240 | `0x1E66B0` | `0x1E66F0` | `0x1E6130` | `0x1E62E0` | `0x1E6040` | `0x1E5F80` | `0x1E61A0` | `0x1E6670` |

`GetUnitCurrentOrder` 的 1.26 `0x3C7780`、1.27 `0x1E5F80` 与技能文档里已核实的地址相同。1.27 `GetWidgetWorldPos` 仍是 `0x03B720`。

结构特征在 11 个 `game.dll` 里的出现次数：

| 特征 | 1.0.17–1.21 | 1.22–1.27 |
| :--- | :--- | :--- |
| `lea eax, [ecx+164h]; ret` | 每个版本 1 处 | 每个版本 3 处（其中 `CUnit::vtable+0xB8` 已在 1.26 / 1.27 对上 RTTI） |
| `mov r, [esi+19Ch]` 这种当前指令 ID 对 | 有 | 有。1.24.4 / 1.26 / 1.27 的 `GetUnitCurrentOrder` 都读这对 |
| `mov ecx, [ecx+1ECh]`（`CAbilityMove`） | 有 | 有 |
| `mov eax, [eax+208h]`（飞行高度） | **没有这条编码** | 有。1.26 / 1.27 的 `GetUnitFlyHeight` 就是它 |

1.0.17 和 1.21 的 `GetUnitX` / `GetUnitMoveSpeed` 外壳是旧式 JASS 帧（先取全局虚机，再 `call` 进对象），没有展开到最后一条字段读取。这两段的字段偏移先按上面的特征字节算“二进制里存在”，不要当成已经和 1.27 逐指令对过。

## 八、实机样本（只读，未调原生）

进程 `war3.exe`，模块 `C:\Program Files (x86)\iCCup Warcraft III\Game.dll`，基址 `0x6D8B0000`，映像大小 `0xCD8000`（与 1.27.0.52240 的 `SizeOfImage` 一致）。用 `CUnit` 虚表 `base+0xA4A704` 扫描，`+0xB8` 槽的 7 字节是 `8D 81 64 01 00 00 C3`。

同一轮里还看到：三只 `ebal` 的 `Amov+0x70` 都是 325、`+0x2CC` 都是 103.648；冰女 `0x11035BF4` 的移速 280、`+0x2CC` 146.458、当时没有当前指令（`+0x19C/+0x1A0` 为 `0xFFFFFFFF`）。地面单位 `+0x208` 都是 0。

没有在游戏线程调用 `GetUnitX` / `GetUnitFacing` / `GetUnitMoveSpeed`。移速是用物编常数对照的，指令 ID 是用 hook 已有的 `0xD000F` 对照的，坐标没有和原生返回值逐个相减。

## 九、还没确认的

1. 代理节点分量到 `GetUnitX/Y` 的完整软浮点公式。站桩样本 300 ms 位移为 0，不能区分 X/Y。
2. `GetUnitFacing` 的角度乘数在运行期的具体值（文件里是 0）。
3. 指令的目标**单位**放在 `COrder` 的哪一对 ID。
4. 碰撞半径，以及寻路器里的下一路径点 / 路径节点列表。
5. 1.0.17–1.21 的字段是否与 1.22+ 逐字节相同。特征在，外壳没跟完。
6. `aiFindAgentInRing` 的环在这局里有没有被冲掉。对象布局和 `JassHandleToUnit` 的返回类型一致，环本身没在进程里对账。
