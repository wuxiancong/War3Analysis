# Dota1 反外挂系统设计方案（对接现有天梯积分系统）

> **结论置顶**
> 1. War3 是**锁步同步（Lockstep）**架构：所有客户端本地完整模拟游戏，主机（War3Bot）只转发动作。因此 **“改数值类”外挂（改金钱/血量/冷却）天然会导致不同步（Desync）**，可由主机比对校验和精准定位；真正的难点是**只读类外挂（全图 MapHack、显隐、自动技能脚本）**。
> 2. 单靠客户端防护一定会被绕过，必须采用 **“客户端完整性 + 主机协议校验 + 回放行为审计 + 天梯统计风控 + 账号设备关联 + 人工复核”** 六层纵深防御。
> 3. 反挂系统与天梯系统的关键接缝是：**结算进入“待确认窗口” → 判挂后可原子回滚积分并补偿受害者**，以及引入 **信誉分（Trust Score）** 参与匹配。
> 4. 现有资产可直接复用：War3Bot 已归档的全量动作流 `.dat`、`0x6B` 战绩管道、HMAC 结算接口、War3Launcher 的注入/Hook 能力、Web 端 3D 轨迹回放与迷雾分析。

## 一、威胁模型：Dota1 常见作弊分类

| 类别 | 典型表现 | 是否改变同步状态 | 主要检测层 |
| :--- | :--- | :---: | :--- |
| **全图 / 去迷雾（MapHack）** | 大地图、小地图显示雾中单位，看到对方 TP/Roshan/插眼 | 否（只读渲染） | 客户端完整性 + 回放“雾中交互”审计 |
| **显示隐身单位** | 看到力丸、赏金、隐身眼位、隐身符 | 否 | 回放“无反隐命中隐身单位”审计 |
| **信息类辅助** | 显示敌方冷却、物品、施法范围、技能弹道 | 否 | 客户端完整性 |
| **自动技能 / 秒控脚本** | 跳刀进场 0 反应时间羊/晕、自动补刀、自动躲技能 | 否（但产生非人类动作） | 回放反应时间 / 动作节律统计 |
| **数值修改（内存改钱/改血）** | 本机数值异常 | **是** | 主机校验和比对 → Desync 定位 |
| **协议伪造** | 伪造动作包、篡改 `0x6B` 战绩、伪造他人离线 | 视情况 | 主机协议校验 + 多端一致性投票 |
| **网络恶意（Lag 攻击/拔线）** | 故意卡顿、关键团战拔线逃跑 | 否 | 主机网络监控 + 强退惩罚 |
| **天梯舞弊（非外挂）** | 互刷分、送人头、小号代练、多开 | 否 | 统计风控 + 设备/IP 关联图谱 |

## 三、L1 客户端完整性（War3Launcher 侧）

客户端防护的目标不是“不可破解”，而是**提高作弊成本 + 为服务端提供证据信号**。

1. **代码段完整性校验**
   - Launcher 已掌握 1.24e/1.26a/1.27a/1.27b 的 `Game.dll` 版本识别与 Hook 能力，可对 `Game.dll` / `Storm.dll` 的 `.text` 段做**分块哈希**；
   - 重点监控**迷雾渲染、小地图绘制、单位可见性判定**等常见 MapHack 补丁点（偏移按版本建表，详见迷雾实现分析文档）；
   - 白名单：Launcher 自己的合法补丁（FPS 解锁、视距、改键、地图大小解锁）必须登记“预期字节”，否则会误报。
2. **模块与注入检测**：周期枚举进程模块，比对签名/哈希白名单；检测 `LoadLibrary` 远程线程、手动映射（无模块头的可执行内存页 `MEM_PRIVATE + PAGE_EXECUTE_*`）。
3. **外部读写检测**：扫描其他进程持有的 War3 进程句柄（`PROCESS_VM_READ/WRITE`），识别外部读内存型全图。
4. **反调试与自保护**：检测调试器、关键代码混淆/加壳（如 VMProtect 处理检测逻辑），检测逻辑随版本热更新。
5. **服务器挑战应答心跳（核心）**
   - 主机每 30~90 秒随机下发 `SC_AC_CHALLENGE{nonce, 区域ID列表}`；
   - 客户端返回 `HMAC(nonce || 指定内存区域哈希 || 模块列表摘要, 会话密钥)`；
   - **超时 / 应答错误 / 连续缺失** 都记为风险信号，杜绝“直接屏蔽检测模块”。
6. **设备指纹（HWID）**：硬盘序列号、主板 UUID、MAC、CPU 信息等加盐哈希后上报，仅存哈希，用于封禁与小号关联。

> [!WARNING]
> 客户端扫描必须明确告知用户并获得同意（用户协议），只采集与反作弊相关的最小数据，不上传文件内容与隐私信息。

## 四、L2 主机实时协议校验（War3Bot 侧）

### 1. 校验和比对定位改数值外挂
- W3GS 中客户端定期发送 `W3GS_OUTGOING_KEEPALIVE (0x27)`，携带当前帧的**游戏状态校验和**；
- **现状**：[`client.cpp`](../../War3Bot/src/client.cpp) 的 `case W3GS_OUTGOING_KEEPALIVE`（约 L1999）已解析出 `unknownByte` 与 `checkSum`，但目前仅用于日志与刷新 `lastResponseTime`；P0 只需按“第 N 个 0x27 ↔ 第 N 个 0x0C 动作帧”序号把校验和存入每帧的比对表即可；
- War3Bot 对同一帧收集 10 个校验和，**少数派即异常方**：
  - 1 人与其余 9 人不一致 → 高度怀疑该玩家内存改数值（或客户端版本/地图被篡改）；
  - 记录 `desync_event{matchId, frame, player}`，该局对其结算冻结，进入审计。

### 2. 动作包合法性
- 复用《动作 ID 载荷长度审计》：未知 Action ID、长度不符、单帧动作数异常 → 丢弃并记录；
- 动作频率上限：持续 APM 远超人类上限（如 > 600 且无回落）→ 标记脚本嫌疑；
- `0x6B SyncStoredInteger` 由每个客户端各自发送：**以 10 端多数投票**作为权威战绩，某端独有/冲突的键值视为篡改，直接拒收。

### 3. 网络行为
- 记录每位玩家 RTT、丢包、“等待玩家”触发次数与时长；
- 团战窗口（附近英雄死亡前后 10 秒）内主动断线 → 与现有强退惩罚叠加“恶意拔线”标签。

### 4. 实时命中事件
- 所有 L2 命中写入 `ac_detections` 并随 `.dat` 一起投递审计服务，作为 L3 的先验。

## 五、L3 回放行为审计（核心：抓只读外挂）

War3Bot 已为每局保存 Zlib 压缩的全量动作流 `.dat`，这是抓全图的最强证据来源。

### 1. 可见性重建：两种精度
| 方案 | 做法 | 精度 | 成本 |
| :--- | :--- | :---: | :--- |
| **近似重建** | 用英雄轨迹（移动/施法目标点推算）+ 视野半径 + 已知眼位，按格子估算各队可见区域 | 中 | 低，纯算法，可批量跑全部对局 |
| **回放复算（推荐用于复核）** | 审计机上运行真实 War3（Launcher 无头/观战模式）加载回放，Hook 可见性判定函数，在每个可疑动作帧查询“目标单位对下令玩家是否可见” | **精确** | 高，只对 L3 初筛高风险局执行 |

### 2. 核心指标
1. **雾中目标交互（Fog Interaction）**：`0x12` 对目标对象下令、`0x16/0x19` 选中敌方单位时，该单位对下令玩家**不可见** → 强证据（正常客户端无法点中雾中单位）。
2. **隐身命中（Invisible Targeting）**：在无真视（宝石/显影之尘/岗哨/反隐技能）条件下，对隐身单位下令或精准释放点技能。
3. **雾中小地图 Ping**：`0x68` 盟友信号点落在敌方雾中英雄位置附近且多次命中。
4. **信息不对称决策**：
   - 敌方雾中 Gank 接近时的**撤退提前量**分布（对比同分段基线）；
   - 盲插眼/盲放技能命中雾中英雄的频率；
   - 雾中 Roshan、对方 TP 落点的“预判”拦截率。
5. **反应时间（脚本检测）**：敌方英雄进入视野 / 跳刀落地 → 本方控制技能下令的间隔；人类通常 > 150ms，分布宽；**稳定 < 80ms 且方差极小** → 自动技能脚本。
6. **动作节律熵**：点击间隔分布的熵、周期性（FFT 峰值）、完全相同的坐标重复 → 宏/脚本。

### 3. 评分方式
- 每个指标输出 `0~1` 的可疑度，按证据强度加权；**强证据（雾中交互、隐身命中）单项即可进入复核**，弱证据（撤退提前量、节律）需累计多局；
- 采用“**跨局累积**”：单局偶然（如刚好眼位视野、技能弹道残留）容易误报，同一账号 N 局持续偏离基线才处罚。

> [!IMPORTANT]
> 必须处理合法视野来源：盟友共享视野、眼/岗哨、技能（先知的电子视野、虚空的时间结界等）、真视宝石、建筑与小兵视野、地图揭示效果。未建模的视野源是最大的误报来源，回放复算方案可避免此问题。

## 六、L4 天梯统计风控（复用天梯数据）

基于 `ladder_stats` / `match_results`：
- **表现突变**：Performance 评分对自身历史与同分段分布的 Z 分数 > 3 且持续；
- **胜率/上分速度异常**：新号前 20 局胜率 > 85% 且平均 KDA 远超同分段 → 代练/小号或外挂；
- **英雄与时间段异常**：某账号仅在特定时间段/设备上表现突变（账号共享、代练）；
- **互刷图谱**：玩家对 A/B 经常出现在对立面且一方持续送人头（`Data:Hero<victim>=<killer>` 中同一 killer-victim 对占比异常）、短时局反复出现 → 构建“对局共现图”，用社区发现找刷分团伙；
- **投降/挂机**：长时间无动作（APM≈0）、只在泉水移动。

## 七、L5 账号与设备关联

- 维护 `账号 ↔ HWID ↔ IP` 二部图，计算关联簇；
- 封禁可按 **账号 / HWID / 关联簇** 三个粒度执行；被封 HWID 上的新号自动降信誉；
- 同一 HWID/IP 的多个账号出现在同一局对立两侧 → 直接判定该局无效（防自刷）。

## 八、L6 风险处置与天梯系统对接

### 1. 结算“待确认窗口”
现有流程：`Global:Winner → LadderScoreEngine::calculate → applyMatchSettlement → POST /api/ladder/settle`。
改造为两阶段：
1. **即时结算（临时生效）**：照常加减分并通知玩家，`matches.ac_status = 'PENDING'`；
2. **审计完成（通常 5~30 分钟）**：`CLEAN` → 定稿；`SUSPECT` → 进复核；`CHEAT` → 触发回滚。
- 若玩家本局实时命中强证据（校验和少数派、`0x6B` 篡改），**直接不结算**，`ac_status='FROZEN'`。

### 2. 判挂后的积分回滚与补偿
- 新增特权接口 `POST /api/ac/verdict`，沿用 HMAC-SHA256 + Nonce + 时间戳防重放；
- 单事务内：
  - 作弊者：撤销本局（及追溯窗口内涉案对局）所得积分，额外扣分，清零连胜；
  - 对手方：本局失分**全额返还**（“受害者补偿”），并推送通知（复用 `0x31` 结算通知/托盘卡片，新增“补偿到账”样式）；
  - 作弊者队友：保持原结算（避免连坐，也避免被利用为“故意坑队友”）。
- 幂等：以 `(matchId, verdictId)` 为唯一键。

### 3. 处罚阶梯
| 等级 | 条件 | 处罚 |
| :--- | :--- | :--- |
| 观察 | 弱证据累积 | 降低信誉分，匹配优先与低信誉玩家 |
| 警告 | 中等证据 / 首次脚本嫌疑 | 警告 + 本局回滚 |
| 临时封禁 | 强证据复核确认 | 天梯封禁 7~30 天 + 回滚追溯窗口 |
| 永久封禁 | 二次确认 / 协议篡改 / 改数值 | 账号 + HWID 永封，赛季成绩清除 |

### 4. 信誉分（Trust Score）
- 范围 0~100，初始 60；干净对局缓慢上升，命中/被有效举报下降；
- `MatchManager` 撮合时在积分搜索半径之外再加一个**信誉分段**维度，低信誉玩家优先互相匹配（“隔离池”），既保护正常玩家，也不提示作弊者已被盯上。

### 5. 举报与申诉
- 游戏内/Launcher 赛后卡片加“举报”按钮（类型：全图/脚本/送人头/挂机），举报只作为**加权信号**，不能单独定罪；举报准确率高的玩家权重提升；
- 申诉：Web 端提交，复核员结合 3D 回放与证据时间线重新判定，申诉成功则恢复积分并补偿。

## 九、复核后台（War3Angular）

- 案件列表：按风险分排序，展示命中指标、证据强度、历史案件；
- **证据时间线**：每条可疑事件（如“34:12 选中雾中敌方英雄 Riki”）可一键跳转到 Three.js 3D 回放对应时间点，并以“下令玩家视角”渲染迷雾；
- 复核员双人确认机制（永封需两人一致），所有操作写审计日志。

## 十、数据模型（新增表）

```sql
-- 设备指纹（仅存哈希）
CREATE TABLE ac_devices (
  hwid_hash   CHAR(64) PRIMARY KEY,
  first_seen  DATETIME, last_seen DATETIME,
  banned      TINYINT DEFAULT 0
);
CREATE TABLE ac_account_devices (
  user_name VARCHAR(32), hwid_hash CHAR(64), last_ip VARBINARY(16),
  last_seen DATETIME, PRIMARY KEY (user_name, hwid_hash)
);
-- 检测命中（实时 L1/L2 + 离线 L3/L4）
CREATE TABLE ac_detections (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  match_id BIGINT, user_name VARCHAR(32),
  layer TINYINT,            -- 1..5 对应检测层
  rule_code VARCHAR(32),    -- 如 FOG_TARGET / DESYNC_MINORITY / REACTION_BOT
  score FLOAT, game_time_ms INT, evidence JSON,
  created_at DATETIME, INDEX(user_name), INDEX(match_id)
);
-- 案件与判决
CREATE TABLE ac_cases (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  user_name VARCHAR(32), risk_score FLOAT,
  status ENUM('OPEN','REVIEWING','CHEAT','CLEAN','APPEALED'),
  verdict_by VARCHAR(32), verdict_at DATETIME
);
CREATE TABLE ac_bans (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  target_type ENUM('ACCOUNT','HWID','CLUSTER'), target VARCHAR(64),
  reason VARCHAR(64), expires_at DATETIME NULL, case_id BIGINT
);
-- 天梯表扩展
ALTER TABLE matches      ADD COLUMN ac_status ENUM('PENDING','CLEAN','SUSPECT','CHEAT','FROZEN') DEFAULT 'PENDING';
ALTER TABLE ladder_stats ADD COLUMN trust_score TINYINT DEFAULT 60;
```

## 十一、协议扩展（Launcher ↔ Server / Bot）

| 包 | 方向 | 内容 |
| :--- | :--- | :--- |
| `CS_AC_HELLO` | C→S | 客户端版本、AC 模块版本、HWID 哈希、模块摘要 |
| `SC_AC_CHALLENGE` | S→C | `nonce`、待校验区域 ID 列表、截止时间 |
| `CS_AC_HEARTBEAT` | C→S | `HMAC(nonce‖区域哈希‖模块摘要)`、序列号 |
| `CS_AC_REPORT` | C→S | 客户端本地命中（可疑模块/句柄/补丁点） |
| `CS_PLAYER_REPORT` | C→S | 玩家举报（matchId、被举报人、类型） |
| `SC_AC_NOTICE` | S→C | 处罚 / 补偿通知（接入托盘通知中心） |

- 所有 AC 包使用会话密钥加密 + 单调序列号，防重放与中间人篡改；
- 天梯房间**强制要求**有效 AC 会话：`CS_AC_HELLO` 未通过或心跳缺失的玩家禁止进入天梯匹配，局内掉线超时视为强退。

## 十二、落地路线图

| 阶段 | 内容 | 收益 |
| :--- | :--- | :--- |
| **P0（1~2 周）** | 校验和少数派检测、`0x6B` 多端投票、动作包合法性/频率校验、结算 `ac_status` 字段与回滚接口 | 立刻封堵改数值、刷战绩、协议伪造 |
| **P1（2~4 周）** | HWID 指纹、账号关联、同设备对立判无效、举报入口、复核后台雏形 | 打击小号互刷与代练 |
| **P2（4~8 周）** | 离线审计 Worker：近似可见性重建、雾中交互/隐身命中/反应时间/节律指标 | 开始批量抓全图与脚本 |
| **P3（持续）** | Launcher 代码段校验 + 挑战应答心跳、回放复算审计机、信誉分隔离池、模型迭代 | 纵深防御与长期对抗 |

> [!TIP]
> 处罚采用**延迟批量封禁（Ban Wave）**：检测到后不立即封，攒一批后统一执行，避免外挂作者通过“哪个版本被封”快速定位检测点。

## 十三、误报控制原则

1. 强证据单项可立案，**弱证据只能累积**，处罚前必须达到跨局阈值；
2. 所有阈值先“影子模式”运行 2~4 周，只记录不处罚，用人工抽检校准误报率（目标 < 0.1%）；
3. 合法补丁（Launcher 自带 FPS/视距/改键）登记白名单；
4. 永久封禁必须有可复现证据（回放时间点）+ 双人复核；
5. 保留完整审计日志，支持申诉复盘。
