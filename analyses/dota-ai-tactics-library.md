## 一、结论

| 问题 | 结论 |
| :--- | :--- |
| 怎么组织？ | **技巧 = 触发条件 + 带真人延迟的动作序列**。两级作用域：**通用**（所有英雄）/ **英雄专属**（表内英雄）；11 个分类：打野、击杀、逃命、补刀、插眼、推线、团战、加点、肉山、防御、欺骗。 |
| AI 怎么用？ | 每个技巧可 `tactic on/off` 自动触发，也可 `tactic run` 手动执行一次；调度按优先级 **逃命 > 救队友 > 切鬼手 > 击杀 > 团战 > 推线 > 打野/加点**，同一时刻只执行一个动作序列；执行期间补刀例程让出控制权。 |
| 需要新逆向吗？ | **不需要新 game.dll RVA。** 新增的都是按名缓存的只读 JASS 原生（物品栏、三维、蓝量）+ 已有 Enqueue 动作包（`useslot1..6 = 0xD0028..0xD002D` 用物品）。 |
| 全都能做吗？ | 不能。**26 项里 18 项已可执行（READY）**，8 项缺底层能力（树木目标、弹道识别、眼位/地形坐标库、Shift 队列标志位、卡尔切球状态、骨法守卫类型、肉山流程）只入目录，`tactic run` 会说明原因。 |

## 四、架构

```text
RemoteControl / 游戏内  tactic list|status|stop|on|off|run
        │  (AI_UNIT_CMD_TACTIC，aux = 技巧 ID / 0x8000|分类 / 0xFFFF 全部)
        ▼
 war3hook_ai.cpp  aiTick (10ms, 游戏主线程)
        │
        ├─ aiTickTactics
        │     ├─ aiScanCamps            每 1s：Player(12) 中立单位首现位置聚类 → 野点表
        │     ├─ aiTickTacticRun        执行当前动作序列（MOVE/ATTACK/STOP/CAST/ITEM，步间真人延迟）
        │     ├─ aiTickCreepBlock       状态机：新一波 → 领头兵前方 Z 字走位
        │     ├─ aiTickStack            状态机：:45 就位 → :53 出手 → 带走 → :00 计数
        │     ├─ aiTickFarmStacked      清野（含英雄清野技能）
        │     └─ 每 200ms 按优先级评估已开启的技巧 → 触发 aiStartTacticRun
        │
        ├─ aiTickRoutine（补刀）     g_aiTacticBusyUntil 期间让出；成功补刀回调 aiTacticOnLastHit
        └─ 施法保护 g_aiCastGuardUntil  技巧施法也会设置（持续施法不被打断）
```

### 新增底层能力

| 能力 | 实现 | 说明 |
| :--- | :--- | :--- |
| 蓝量 / 最大血量 | `GetUnitState(u, 2)` / `(u, 1)` | 连招判断「蓝够全套」 |

## 五、命令

```text
tactic list                         # 目录（分类 / 通用或英雄 / 开关 / 是否只入目录）
tactic status                       # 游戏钟、物品栏、蓝量、视野内单位、野点表、正在执行的技巧
tactic on  <key|分类|all>           # 开启自动触发（目录项不会被开）
tactic off <key|分类|all>
tactic run <key> [p1 p2 p3]         # 立即执行一次
tactic stop                         # 中止正在执行的技巧（含拉野 / 卡兵 / 清野）
```

## 五点五、卡兵成功的判定与成功率

### 怎么验证卡兵成功

卡兵的目的不是「把兵挡住不动」，而是**让己方兵线晚到河道**，两边兵在更靠己方塔的位置相遇（中路对线更安全，敌方要多走路才能补刀 / 压线）。所以用**结果**判定，不用「走了多少步」：

```text
起点   = 刷兵 1s 后领头兵位置（兵营门口）
终点   = 领头兵走到河道（中路距地图中心 ≤ 1300）
实际用时 = 终点时刻 - 起点时刻
理论用时 = 起点到终点的直线距离 / 兵速 325
延迟   = 实际用时 - 理论用时
延迟 ≥ 2.0s → ✅ 卡兵成功（相遇点约往己方移 325 以上）
```

- **基线**：`tactic run block 1` 只测量不卡。兵互相挤、绕路本身也会有一点「自然延迟」，卡兵延迟要明显高于基线才算有效。
- 每波日志：`📏 卡兵结果 第 N 波：到河道 x.xs，直线 d，理论 y.ys，延迟 z.zs ✅/❌ | 成功 s/w（%）平均延迟`；`tactic status` 汇总成功率 / 平均延迟 / 基线 / 无效波数。
- 领头兵途中死亡（被敌方英雄打死等）的波记为**无效**，不计入成功率。
- 只统计**中路**（领头兵在地图对角线附近）。

### 能不能保证 100% 成功

**不能保证 100%**，只能把成功率尽量做高并用数据证明。原因：

| 因素 | 说明 |
| :--- | :--- |
| 刷兵时英雄不在门口 | 回城、被追、在打野、补给时错过本波（连续模式会提前 12s 回门口，但英雄死亡 / 被拖住时赶不上） |
| 兵的寻路是引擎决定的 | 兵发现前方被挡会绕行，绕行方向与碰撞体积、地形（中路坡道、树、塔）相关，每波略有不同 |
| 真人化抖动 | 走位间隔 150~520ms、左右摆动是刻意加的随机，偶尔会让兵从侧面绕过去 |
| 英雄体型与移速 | 碰撞体积小 / 移速低的英雄卡兵效果本身更差（这是游戏机制） |
| 远程兵 / 攻城车 | 只卡领头近战兵；后面的兵不受影响 |
| 对手干扰 | 敌方英雄压过来、打断走位时只能放弃 |

能提高成功率的方向（按需再做）：根据兵的实际运动方向调整挡位侧（兵往左绕就往左挡）；每波前精确站到兵营门口正前方；碰撞小的英雄降低期望。**验收标准建议用「成功率 + 平均延迟高于基线」而不是 100%。**

### 实测（2026-11-17，第二台机器 Windows Server，冰女，中路，近卫）

测量方法迭代：

| 版本 | 终点 | 问题 |
| :--- | :--- | :--- |
| 1 | 领头兵到河道 | 越往后两边兵越早在河道前交战，领头兵死在半路 → 整波作废 |
| 2 | 离兵营门口直线 **1500** | 基线时英雄仍站在门口路线上，本身就挡兵 → 基线偏高 |
| 3 | 同上；基线时英雄站门口侧面 450 | 当前版本。阈值 = 基线平均 + 1.5s |

| 轮次 | 基线（10 波，不卡） | 卡兵 | 成功率 |
| :--- | :--- | :--- | :--- |
| 卡兵算法 v1（跟「刷兵时最近的兵」、方向取兵上一帧位移、走位中位 260ms） | 平均 1.3s（英雄挡路，偏高） | 延迟 14.4 / 2.6 / 1.5 / -0.1 / 0.1 / 0.5 / 2.1 / 0.7s | **1/8（12%）** |
| 卡兵算法 v2（跟沿车道最靠前的兵、方向固定朝中路、兵往哪侧绕就挡哪侧、走位中位 170ms） | 平均 **2.0s**（0.1~4.9s） | 延迟 20.6 / 0.2 / 3.5 / 1.9 / 0.2 / 0.8 / 0.6 / … s | **2/8（25%）**，平均延迟 3.6s |

结论：

- 每一波都确实在卡（英雄提前在门口、每波 50~58 次走位，英雄被兵顶着只走到约一半兵速），但**总有一只兵从侧面溜过去**，按「刷兵时离英雄最近的那只兵」测量时就是「没卡住」。
- 每轮第一波都是 14~20s 的大延迟（英雄从侧面 / 等待位切入时恰好挡在兵群正前方），之后回到门口正前方反而容易被绕过 → 站位相对兵群的角度是关键。
- 当前成功率远不到 100%，也不该承诺 100%。

下一步（未做）：

1. 测量改为**兵线前沿**：本波所有兵里最先走到 1500 的时刻（相遇点由最前面的兵决定，比跟单只兵更合理）。
2. 卡兵改为挡在兵群前沿的**中间偏绕行侧**，并在兵即将从侧面越过英雄时横移拦截；每波前站位改为门口斜前方（复现第一波大延迟的切入角度）。
3. 换移速高、碰撞大的英雄对比（冰女移速 280 < 兵速 325，本身是最难卡的一类）。

测试环境问题（与卡兵无关，记录备查）：

| 问题 | 现象 | 处理 |
| :--- | :--- | :--- |
| 游戏钟误校准 | 读图时地图预放的中立单位也走 CreateUnit，被当成 0:30 野怪 → 钟快约 2 分钟 | 只认第一波兵后 15~60s 内的中立单位创建（已修） |
| `load.dll` 删除挂起 | `killgame` 后 Launcher / PerformanceAnalyzer 仍持有游戏目录 `load.dll` 句柄 → 下次启动复制失败（状态码 141） | 临时：退出 Launcher + 结束 Analyzer 后再启动。**Launcher 待修** |
| 加入房间 BADPASSWORD（错误码 429） | 多次强杀后 bnetd / Bot 残留同名房间 `AI_DEBUG` → war3 加入旧房间 | 临时：bnetd + Bot + Launcher 全部重启；或换房名（DebugConfig `RoomName`）。**待修：killgame 后通知 Bot/bnetd 关闭房间** |
