## 核心结论速览（直答用户三问）

1. **「三路兵线的移动速度是如何变化的？每一路的速度都不一样吗？」**
   - **所有兵种（近战/远程/超级兵/攻城车）的基础移速均为 `325.0`**（`CAbilityMove+0x70 = 325.0f`）。
   - 但在**前 7 分钟（准确条件是全局计时器 `TimerGetElapsed(M) < 420.0s`）**，出兵函数 `SPO` 会给**四条边路的近战与远程小兵**（不含攻城车、不含中路）挂上持续 **严格 `15.0s`** 的自生光环：
     - **优势路（近卫下路、天灾上路）**：挂 `A2V1`（Buff `B0H2`），修改 `CAbilityMove+0x78` 乘数为 **`1.250`**，面板与物理步进速度上限升至 **`406.25`**（`+25%`），15 秒大约跑到车道 `s ≈ 6000~6150`（刚过二塔、进入一塔前弯道区）时移除光环，恢复 **`325.0`**。
     - **劣势路（近卫上路、天灾下路）**：挂 `A2V0`（Buff `B0H1`），修改 `CAbilityMove+0x78` 乘数为 **`0.750`**，面板与物理步进速度上限降至 **`243.75`**（`-25%`），15 秒大约跑到车道 `s ≈ 3500~3650`（刚过二塔）时移除光环，恢复 **`325.0`**。
     - **中路（近卫中路、天灾中路）**：全程不挂任何移速光环，`CAbilityMove+0x78` 恒为 **`1.000`**，全路段恒为 **`325.0`**。
2. **「难道还随时间变化？」—— 不仅随时间变化，而且 `war3map.j` 存在一个导致光环在游戏钟 `4:15 ~ 5:20` 就提前结束的计时基准偏移！**
   - **每波内部随时间变化**：前 7 分钟内，边路每波兵刷出后的 `0 ~ 15.0s` 为 `406.25`（优势路）或 `243.75`（劣势路），第 `15.0s` 计时器 `AW1` 触发移除光环后瞬间变回 `325.0`。
   - **全局随局时变化（重大发现）**：`SZO` / `SVO` 检查的是 `TimerGetElapsed(M) < 420`，但计时器 `M` 在**地图加载完成时（`main()`）就已启动**，而 `0:00` 出兵号角响时地图用 `N = TimerGetElapsed(M)` 记录了号角前选人耗时（`-ap` 模式 `BL=90s`，实测 `N ≈ 100~106s`；`-rd` 模式 `N ≈ 135s`；`-xl` 模式 `N ≈ 165s`；`-cm` 模式 `N > 180s`）。因为 `SZO` / `SVO` **忘记减去 `N`**，边路光环实际在**游戏出兵钟 `t_game = 420 - N`** 就提前停止发放：
     - `-ap` / `-ar` / `-sd`：**游戏钟 `5:14 ~ 5:20` 停止**（仅第 1~11 波 `0:00~5:00` 有光环，**第 12 波 `5:30` 起已无光环**！）；
     - `-rd`：**游戏钟 `~4:45` 停止**（第 10 波 `4:30` 为最后一波）；
     - `-xl`：**游戏钟 `~4:15` 停止**（第 9 波 `4:00` 为最后一波）；
     - `TimerGetElapsed(M) >= 420.0s` 之后，**六路所有小兵全时段、全路段恒为 `325.0`**（每 7.5 分钟一次的 `TQO` 兵线升级只加攻击力和生命值，不加移速；超级兵、攻城车、昼夜交替均不改变移速）。
3. **「或许下路根本不需要卡兵？」—— 用户直觉完全正确！优势路（近卫下 / 天灾上）前 7 分钟绝不该卡兵（7 分钟后也最多只可微卡 `≤1.5s`）！**
   - **物理上卡不住**：前 15s 小兵移速 `406.25`，任何英雄（冰女 `280`，最快英雄无鞋 `325`）在兵营门口都会在 `2.5s` 内被整波超车（实测门口起卡 `0~12` 分）；即便改到 `s = 6400`（15s 加速结束处）再卡，此时距一塔（`s = 8450`）仅剩 `2050` 距离（不卡仅需 `6.7s`），且正处近卫下路最急的 S 形双弯道（`s = 6600..8000`），算分公式要求按全长 `8700` 拖慢 `12.8s` 才给满分，物理天花板被锁死在 `47` 分左右。
   - **战术上卡兵是负收益（反控线）**：IceFrog 设计优势路 `+25%`、劣势路 `-25%`，正是为了补偿优势路（近卫下 `8776`、天灾上 `7427`）比劣势路（天灾下 `5512`、近卫上 `5752`）长 `2000~3200` 的不对称距离，使双方不卡兵时恰好在**优势路一塔外 `+2081`（近卫下）/ `+3006`（天灾上）**安全交汇；到了 7 分钟后两边同速 `325`，近卫下路不卡兵的自然交汇点已收缩到一塔外 **`+911`**，此时只要把近卫下路兵卡慢 **`2.2s` 以上**（例如拖慢 `3.0s`，交汇点变成一塔外 `+446`），**天灾兵线就会直接冲进近卫下路一塔射程（`<650`）**，导致防御塔把兵线反推向天灾塔下！
   - **最该卡的是劣势路（近卫上 / 天灾下）前 7 分钟与中路全时段**：劣势路前 15s 小兵仅 `243.75`，`280` 移速的冰女比兵快 `+36.25`，门口起卡轻松拿 **`91~100` 分**（拖慢 `16~22s`，把离塔 `+3144` 的危险兵线拉回己方一塔前）；中路全时段 `325`，拖慢 `3~5s` 即可把交汇点从河道中心拉上己方高坡。

### 1.2 重大发现：`TimerGetElapsed(M)` 未减号角前时间 `N`，导致光环在游戏钟 `4:15 ~ 5:20` 提前结束！

> [!IMPORTANT]
> 旧文档 `dota-lane-creep-speed-profile.md` 与当前卡兵代码 `war3hook_ai_tactics.inl`（`aiBlockBoostActive`）均误以为「前 7 分钟 = 从第一波出兵（`0:00`）起算的 420 秒（共 14 波兵，`0:00 ~ 6:30`）」。**经 `war3map.j` 全链路追踪与实机 CSV 核对，这一假设是错的！**

我们在 `war3map.j` 中追踪全局计时器 `M`、出兵倒计时器 `OL` 与时间戳变量 `N` 的完整生命周期：

1. **地图加载即启动 `M`（`L7395` / `L91547`）**：
   - 在 `main()` 初始化函数 `K`（`L7395`）中，地图加载完进入游戏画面（`-ap` 弹出模式选择提示前 `t = 0`）就立即执行：
     ```jass
     call TimerStart(M, 99999.00, false, null)
     ```
2. **模式选择后启动号角倒计时 `OL`（`VU2` `L32775..L32796`）**：
   - 模式确定后（通常在加载后 `10~16s`），`VU2` 根据模式设置选人准备时间 `BL` 并启动倒计时器 `OL`：
     - `-cm` / `-lm` / `-mm` / `-vr`：`BL = 180`（外加 BP 暂停耗时）
     - `-xl`：`BL = 150`
     - `-rd`：`BL = 120`
     - `-ap` / `-ar` / `-sd` / 普通模式：`BL = 90`
     ```jass
     call TimerStart(OL, BL + 1, false, null)
     ```
3. **`0:00` 出兵号角响时记录 `N = TimerGetElapsed(M)`（`IU2` `L27823..L27847`）**：
   - 当 `OL` 倒计时归零（游戏正式吹响 `0:00` 号角、刷出第 1 波兵）时，`IU2` 执行：
     ```jass
     set N = TimerGetElapsed(M)
     ...
     call TriggerRegisterTimerEvent(ZG, 30, true)
     call TriggerExecute(ZG) // 0:00 刷出第 1 波兵
     ```
   - 在计算买活价格的函数 `GV1`（`L7139`）中，作者正确减去了 `N`：`R2I(TimerGetElapsed(M) - N)`（这才是 `0:00` 号角后的真实对局时间 `t_game`）。
   - **但在 `SZO`（`L23020`）和 `SVO`（`L23031`）中，作者直接写了 `if (TimerGetElapsed(M)) < 7 * 60`，完全没有减去 `N`！**

因此，边路加速/减速光环真正生效的对局时间窗口是 **`t_game = TimerGetElapsed(M) - N < 420.0 - N`**：

| 游戏模式 | 选人倒计时 `BL` | 号角响时 `N = TimerGetElapsed(M)` | 光环实际结束的游戏钟 `t_game = 420 - N` | 带光环的波次范围（每 30s 一波） | 第一波**无光环（恢复 325）**的波次 |
|---|---|---|---|---|---|
| **`-ap` / `-ar` / `-sd` / 默认** | `90s` | **`100 ~ 106s`**（`15s` 模式选择 + `91s` 倒计时） | **游戏钟 `5:14 ~ 5:20`**（出兵后 `314~320s`） | **Wave 1 (`0:00`) ~ Wave 11 (`5:00`)** | **Wave 12 (`5:30`，`t_M ≈ 435s`)** |
| **`-ap` + `-test` / 快速开局** | `90s`（或跳过部分等待） | **`105 ~ 150s`** | **游戏钟 `4:30 ~ 5:15`** | **Wave 1 (`0:00`) ~ Wave 10/11** | **Wave 10~12 (`4:30 ~ 5:30`)** |
| **`-rd`（随机征召）** | `120s` | **`~135s`** | **游戏钟 `~4:45`**（出兵后 `285s`） | **Wave 1 (`0:00`) ~ Wave 10 (`4:30`)** | **Wave 11 (`5:00`)** |
| **`-xl`（扩展阵容）** | `150s` | **`~165s`** | **游戏钟 `~4:15`**（出兵后 `255s`） | **Wave 1 (`0:00`) ~ Wave 9 (`4:00`)** | **Wave 10 (`4:30`)** |
| **`-cm`（队长模式）** | `180s` + BP 耗时 | **`195 ~ 450s+`** | **游戏钟 `≤ 3:45`**（若 BP 超 5m10s 则开局即 0 波） | 最多 Wave 1 ~ Wave 8 | Wave 9 (`4:00`) 或更早 |

**实机 CSV 铁证（直接解释了此前未解的异常现象）**：
- 在 `records/block/cm/cm_bot_20261121-070328_5waves_pass0_avg38.csv` 中：
  - **Wave 8（对局刷兵 `3:30`，`t_M ≈ 330s < 420s`）**：前 15 秒从 `s = 637` 狂奔至 `s = 6309`，实测区间速度 **`381.0 ~ 392.4/s`**（明确带有 `A2V1` `+25%` 加速）；
  - **Wave 10（对局刷兵 `4:30`，因该局选人+等待耗时 `N ≈ 155s`，此时 `t_M ≈ 425s > 420s`）**：从出兵口起前 15 秒仅从 `s = 632` 走到 `s = 4689`，实测出兵段速度直接掉回 **`287.2 ~ 305.0/s`**！
  - 而 `war3hook_ai_tactics.inl` L2849 的 `aiBlockBoostActive()` 写的是 `GetTickCount64() < g_aiFirstWaveTick + 420000`（从收到 `-block start` 看到的第一波兵起算 420 秒），导致在 Wave 10、Wave 12 小兵根本没有加速的情况下，AI 仍然跑到 `s = 6400` 傻等，白白丢掉 `s = 600..6400` 整整 `5800` 距离的卡兵机会（`joinSeconds` 高达 `19.2 ~ 22.0s`）！

### 1.3 每波持续时间（严格 `15.0s`）与跨 `420s` 边界的切换行为

`AX1` 与 `AW1` 的 `war3map.j` 原文（`L5068..L5102`）：

```jass
function AW1 takes nothing returns nothing
    local trigger t = GetTriggeringTrigger()
    local integer h = GetHandleId(t)
    local unit u = LoadUnitHandle(HY, h, 2)
    local integer JMR = LoadInteger(HY, h, 40)
    local integer abilId = LoadInteger(HY, h, 41)
    if GetUnitAbilityLevel(u, JMR) == 0 and GetUnitAbilityLevel(u, abilId) == 0 then
        call FlushChildHashtable(HY, h)
        call DestroyTrigger(t)
    else
        call UnitRemoveAbility(u, JMR)
        call UnitRemoveAbility(u, abilId)
        if GetUnitAbilityLevel(u, JMR) > 0 or GetUnitAbilityLevel(u, abilId) > 0 then
            call AZ1(u, JMR, abilId) // 若单位正处于无敌/暂停导致移除失败，挂 1.0s 周期重试计时器
        endif
        call FlushChildHashtable(HY, h)
        call DestroyTrigger(t)
    endif
    set u = null
    set t = null
endfunction

function AX1 takes unit u, integer abilId, integer level, real duration, integer JMR returns nothing
    local trigger t = CreateTrigger()
    local integer h = GetHandleId(t)
    call UnitAddAbility(u, abilId)
    call SetUnitAbilityLevel(u, abilId, level)
    call UnitMakeAbilityPermanent(u, true, abilId)
    call SaveUnitHandle(HY, h, 2, u)
    call SaveInteger(HY, h, 41, abilId)
    call SaveInteger(HY, h, 40, JMR)
    call TriggerRegisterTimerEvent(t, duration, false) // duration = 15.00s
    call TriggerAddCondition(t, Condition(function AW1))
    set t = null
endfunction
```

**切换特性**：
1. **单波严格 `15.0s`**：每只边路近战/远程兵在出生瞬间由 `UnitAddAbility` 获得 `'A2V1'` 或 `'A2V0'`，同时绑定一个独立的 `15.0s` 单次触发器；15.0 秒到期时立即调用 `UnitRemoveAbility` 同时剥离 Buff（`'B0H2'` / `'B0H1'`）与技能本体（`'A2V1'` / `'A2V0'`），移速在下一个 32Hz 物理帧立即恢复 `325.0`。
2. **跨 `420s` 边界不中断在途波**：`TimerGetElapsed(M)` 跨过 `420.0s` 的那一刻，并没有全局触发器去剥离在途小兵的光环；如果在 `t_M = 418.0s` 刷出一波兵，这波兵依然会完整享受 `15.0s` 的 `+25% / -25%` 光环直到 `t_M = 433.0s`；而下一波（`t_M = 448.0s`）刷出时因 `SZO`/`SVO` 条件不满足，从出生起就是 `325.0`。

### 3.2 引擎移速计算链（从 `CAbilityMove` 到 32Hz 坐标步进）

通过对 `War3Launcher/versions` 下全部 11 个版本的 `Game.dll` 反汇编交叉核验，War3 引擎的单位移速计算与步进由以下 5 个阶段组成：

1. **阶段 1：面板移速合成与上下限钳制（`CUnit::GetMoveSpeed` → `CAbilityMove::CalcMoveSpeed`）**
   - `CUnit::GetMoveSpeed`（1.27 RVA `0x64F910`，1.26 RVA `0x2AB820`）取出 `this->abilityMove`（`[unit + 0x1EC]`），若非空则调用 `CAbilityMove::CalcMoveSpeed`（1.27 RVA `0x5DF170 → 0x5DF1E0`，1.26 RVA `0x201C60 → 0x2019F0`）。
   - `CAbilityMove::CalcMoveSpeed` 逻辑：
     - 若 `[amov + 0x7C] != 0`（被定身/缠绕），直接返回 `0.0f`；
     - 否则计算 `rawSpeed = ([amov + 0x70] + flatBonus) * [amov + 0x78]`：
       - 优势路前 15s：`325.0f * 1.250f = 406.25f`
       - 常态/中路/攻城车：`325.0f * 1.000f = 325.00f`
       - 劣势路前 15s：`325.0f * 0.750f = 243.75f`
     - 与 `GameplayConstants` 的 `[MinUnitSpeed(100.0f), MaxUnitSpeed(522.0f)]`（1.27 RVA `0x6718E0` / `0x671610`）进行钳制后返回。
2. **阶段 2：群组/单兵速度转网格步进率（`GroupSpeedMin`，1.27 RVA `0x03E900`，1.26 RVA `0x474EF5`）**
   - 将阶段 1 返回的世界移速除以 `32.0f`（IEEE-754 指数减 5：`add eax, 0xFD800000`），转换为 **寻路网格单元速度 `v_cells`（1 cell = 32.0 游戏距离）**：
     - `406.25 / 32.0 = 12.6953125 cells/s`
     - `325.00 / 32.0 = 10.1562500 cells/s`
     - `243.75 / 32.0 = 7.6171875 cells/s`
   - 若指令是玩家框选编队保持队形移动（`groupMoveFlag` 置位），会取编队内最慢单位的 `v_cells`；**但 DotA 6.83d 出兵脚本使用的是 `ForGroup(..., IssuePointOrderById(GetEnumUnit(), 851983, X, Y))` 逐个单位独立下令**，`groupMoveFlag = 0`，因此**攻城车（`325.0`）绝对不会通过编队同速机制拖慢同波的 `406.25` 优势路小兵**，在劣势路也不会被 `243.75` 的小兵拖慢（实测劣势路第 7 波攻城车以 `325` 甩开 `243.75` 的近战/远程兵独自冲在最前）。
   - 计算出的 `v_cells` 同时写入运动节点 `CPoPosCl`（`posNode = [unit + 0x168]`）的两个字段：
     - **`[posNode + 0x88]`（`float maxSpeed_cells`）**
     - **`[posNode + 0xB4]`（`float acc_cells`）**
3. **阶段 3：转身速率与推进窗口余弦缩放（`StepTurnAndMove`，1.27 RVA `0x03EE00`，1.26 RVA `0x4753A0`）**
   - 读取当前朝向与目标局部路点方向夹角 $\Delta\theta = |\theta_{\text{target}} - \theta_{\text{facing}}|$，以及单位推进窗口 $\theta_{\text{prop}} = \text{propWin} = 60^\circ$（$\pi/3 \approx 1.0472\text{ rad}$）：
     - **当 $\Delta\theta \ge 60^\circ$ 时**：**移动速度因子为 `0.0`**！单位在原地以 `turnRate`（小兵 `0.50`、攻城车 `0.40`）纯转身，不产生任何位移（这解释了近卫上路出生 `270° → 90°` 掉头 `180°` 时前 `0.28s` 原地锁死）。
     - **当 $0 < \Delta\theta < 60^\circ$ 时**：移动步长按 $\cos(\Delta\theta) \cdot \frac{\theta_{\text{prop}} - \Delta\theta}{\theta_{\text{prop}}}$ 线性+余弦衰减，边转边加速。
     - **当 $\Delta\theta = 0$ 时**：速度因子为 `1.0`。
4. **阶段 4：零惯性瞬时达速与 32Hz 速度向量合成（`CPoPos::AddVelocity`，1.27 RVA `0x040A10`，1.26 RVA `0x4773B0`）**
   - 当方向对齐后，由于 `[posNode + 0xB4] (acc)` 在阶段 2 被直接赋值为 `[posNode + 0x88] (maxSpeed)`，在单个 32Hz 逻辑帧（$\Delta t = 0.03125\text{s}$）内目标速度即直接拉满到 `maxSpeed_cells`，**直线段不存在物理惯性加速过程（瞬间达到最高速）**。
   - 合成后的网格速度向量写入：
     - **`[posNode + 0x80]`（`float velX_cells`）**，乘以 `32.0f` 即世界速度 $v_x$
     - **`[posNode + 0x84]`（`float velY_cells`）**，乘以 `32.0f` 即世界速度 $v_y$
5. **阶段 5：精确世界坐标合成公式（`GetWidgetWorldPos`，1.27 RVA `0x03B720 → 0x03D790 → 0x03EBF0`）**
   - 此前文档对 `CPoPos+0x78/+0x7C` 为何每 `0.35~0.5s` 跳变一次存疑，本次通过反汇编 1.27 `0x03EBF0` 彻底查明：
     - `[posNode + 0x78]`（`gridX`）与 `[posNode + 0x7C]`（`gridY`）是当前寻路步的**起点网格锚点**；
     - `[posNode + 0x60]`（`t_start`）是该寻路步开始时的**引擎内部 32Hz 仿真时间戳（单位：游戏秒）**；
     - 任意时刻 `t_sim_now` 的精确连续世界坐标由 `0x03EBF0` 实时线性插值合成：
       $$\text{worldX} = \left(\text{gridX}_{[+0x78]} + (t_{\text{sim\_now}} - t_{\text{start},[+0x60]}) \cdot \text{velX}_{[+0x80]}\right) \times 32.0 - 8192.0$$
       $$\text{worldY} = \left(\text{gridY}_{[+0x7C]} + (t_{\text{sim\_now}} - t_{\text{start},[+0x60]}) \cdot \text{velY}_{[+0x84]}\right) \times 32.0 - 8192.0$$

### 4.1 深度复盘：冰女（移速 280）在近卫下路为什么门口起卡 ~3 分、改到 6400 处起卡 47 分？

结合 `records/block/cm/` 下的 7 份 CSV 轨迹与 `war3hook_ai_tactics.inl`（`L1410..1720`、`L2846..3510`）源码，冰女在近卫下路不及格由 **4 个硬性原因** 叠加造成：

1. **前 15 秒（`s = 216..6150`）速度倒挂 `-126.25`，兵营门口起卡必败（平均 ~3 分）**：
   - 前 15s 近卫下路小兵带 `A2V1` 移速为 **`406.25`**（实测 `396~400/s`），而冰女无鞋移速仅 **`280.0`**（即使全 DotA 裸鞋最快英雄月骑/混沌 `325~330` 也比小兵慢 `76~81/s`）。
   - 在兵营门口（`s = 570`）起卡，小兵以 `+120/s` 的相对速度冲向冰女，碰撞触发一次 `0.3s` 侧绕后立即从冰女两侧全员超车；`2.0~2.5s` 内 4 只兵全部越过冰女且再也追不上（`leakCount = 4/4 → leakScore = 0`，`delay < 1.2s → delayScore = 6`，总分 **`3` 分**）。
2. **改到 `s = 6400`（15s 加速结束处）再卡：评分公式 `delayScore` 的数学天花板被锁死在 35~45 分！**
   - 看 `war3hook_ai_tactics.inl` L3489–3494 的 `delayScore` 计算公式：
     ```cpp
     const float baseTravel = lane->atTower / 340.0f; // 8450 / 340 = 24.85s (或有 s_natT 时约为 23.5s)
     const float target = baseTravel * 0.5f;          // 要求拖慢整条路总用时的 50%，即需拖慢 ~11.8s ~ 12.4s 才拿 100 分！
     const int delayScore = (int)(aiClamp(delay / target, 0.0f, 1.0f) * 100.0f + 0.5f);
     ```
   - 当冰女在 `s = 6400` 接兵时，小兵已经用 `15.5s` 跑完了前 `76%` 的路程，**距离终点 `atTower = 8450` 仅剩 `2050` 距离**！
   - 在这仅剩的 `2050` 距离里，不卡的小兵（`310/s`）只需 **`6.6 秒`** 就到一塔了。哪怕冰女在这 `2050` 距离里把小兵完美压到 `185/s`（耗时 `11.1s`），**物理上最多也只能拖慢 `11.1 - 6.6 = +4.5 秒`**！
   - 把 `delay = 4.5s` 代入评分公式：`delayScore = 4.5 / 12.0 * 100 = 37.5 分`！也就是说，**在 `s = 6400` 起卡，即便 0 漏兵（`leakScore = 100`），`delayScore` 也被剩余路程过短锁死在 `35~45` 分**，一旦漏 1~2 只兵，总分 `(leakScore + delayScore) / 2` 就掉到 **`40~52` 分**！
3. **`s = 6400..8200` 正好撞上近卫下路最急的 S 形双弯道，导致 `leakScore` 崩盘**：
   - 小兵在 `406.25` 高速奔跑 15 秒后，4 只兵的纵向队形已被拉长到 `400~600` 距离（远不如出兵口紧凑）。
   - 冰女在 `s = 6400` 刚接上排头兵，兵线立刻进入 `SentinelBot1`（`s = 6120, d = -116`）→ `s = 7300, d = -58` → `s = 8000, d = +91` 的 S 形小树林双弯道。后排小兵寻路切内弯时横向跨度达 `150+`，极易从正在挡排头兵的冰女身侧滑过（实测 `cm_bot_075732` 中 4 波有 3 波漏 2~3 只兵，`leakScore = 25~50`）。
4. **`aiBlockBoostActive()` 计时错位 + 上一波卡完回程迎面撞兵 Bug（`cm_bot_075732` Wave 10/11 实锤）**：
   - 如 1.2 节所述，`war3map.j` 在对局钟 `4:30 ~ 5:20`（Wave 10~12）就已经停止发放 `A2V1` 加速；但 `aiBlockBoostActive()` 从首次启动 `-block start` 算 420 秒，导致 Wave 10、Wave 11 小兵明明是 `325` 常速，冰女却依然在 `s = 6400` 傻等（小兵从出生到 `s = 6400` 用了 `20.5s` 而不是 `15.3s`）。
   - 更致命的是：冰女把上一波兵卡到一塔（`s = 8450`，耗时到下一波出生后 `~18s`）再往回跑到 `s = 6400` 时，在 **`s = 7000..7300` 迎面撞上正在往前走的新一波兵**，把排头兵撞停后再掉头，不仅打乱了队形，还污染了基线波 `s_natT` 的采样。

### 4.4 明确回答：对于优势路前 7 分钟这种没法卡的路段，应该「不计分」还是「降低及格线」？

**结论：必须设为「不计分（免考 / AI 实战自动跳过优势路前 7 分钟卡兵）」，绝不能用「降低及格线」凑合！** 理由有三：

1. **天灾上路前 7 分钟连「6400 处再卡」的空间都没有**：
   - 近卫下路兵营到一塔长 `8776`，15s 光环结束在 `s ≈ 6150`，离一塔还剩 `2626`（到 `atTower=8450` 剩 `2300`）；
   - 而**天灾上路兵营到一塔总长只有 `7427`**！15s 光环（`406.25`）结束在 `s ≈ 6050` 时，**距离天灾上路一塔只剩 `1377` 距离（小兵 4.2 秒就走完了）**！在这里拦截最多只能挡 3~4 下，得分恒在 `30~40` 分，降低及格线毫无鉴别意义。
2. **实战中在优势路卡兵属于「劣化局面的错误操作」**：
   - 考核系统的目的是让 AI 学会正确的 DotA 对线行为。优势路前 7 分钟正确的 AI 行为是**直接去线上/河道抢符或提前占线，让兵线自然在塔外 `+2081` 交汇**，而不是在 `s = 6400` 浪费 15 秒等兵再把兵线卡进自家塔下。如果降低及格线（例如降到 40 分）去鼓励 AI 卡优势路，等于用考核指标强迫 AI 做出违背 DotA 核心机制的蠢事。
3. **代码层面的同步修复建议（供后续改 `war3hook_ai_tactics.inl` 时直接落地）**：
   - **修复 1**：`aiBlockBoostActive()` 不能用 `GetTickCount64() < g_aiFirstWaveTick + 420000`！应直接读取小兵的 `[amov + 0x78]`（`speedMultiplier > 1.1f` 或 `< 0.9f`）或读取地图计时器 `M` 的经过时间 `TimerGetElapsed(M) < 420.0f`；
   - **修复 2**：当检测到当前分路为优势路（近卫下 / 天灾上）且处于 `A2V1` 加速生效期（`[amov + 0x78] > 1.1f`）时，AI 直接跳过卡兵（或评分系统将该波标记为 `SKIP_BOOSTED_SAFELANE` 不计入平均分）；一旦 `TimerGetElapsed(M) >= 420.0f`（`-ap` 模式 Wave 12 / `5:30` 起，`[amov + 0x78] == 1.0f`），若用户在测试近卫下路卡兵，AI 应立即切换为**从兵营门口 `s = 570` 起卡**，此时全程 `8200` 距离都是 `325` 常速，得分将立刻从 `47` 分回升至 `65~85` 分！
